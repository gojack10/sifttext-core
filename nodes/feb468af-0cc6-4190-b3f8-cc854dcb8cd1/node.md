## Entry and required reads
Apply when asked to design or repair a workflow containing bounded model choices. Read the parent Canopy procedure first; then read the assigned project's outcome, constraints, current implementation contract, and the evidence relevant to the proposed decision boundary. When the task touches a serving runtime, read that runtime's current operational rules. When it touches an application harness, read its capability and permission contract. Previously loaded unchanged instructions may be reused. Use only available authorized evidence references; this bundle installs no Decision Models program, serving runtime or controller. Missing capabilities remain gaps, not implied prerequisites or permission to launch a model.

## Default authoring sequence
1. Preserve the user's actual request, interaction style, authority, and completion test. Identify the existing workflow owner. Do not silently redefine an open research question as a navigation task.
2. Identify one repeated choice whose alternatives can be supplied explicitly. Prefer ordinary code when deterministic rules suffice. Consider a decision model only when evidence-dependent bounded selection could avoid general-agent turns; candidate uses include action selection, routing, skill selection, and ranking supplied items. Treat each as a hypothesis until checked.
3. Name the actors: who observes and constructs candidates, who chooses, who supplies generated arguments, who validates and executes, who interprets results, and who owns the original outcome. A decision model does not gain authority because it is fast or confident.
4. Specify the input and executable interface. Each offered action or label must map to an actual supported operation or downstream consumer, with required arguments, validation, and permission checks. If a needed capability is absent, return a capability gap; do not attempt to prompt an unavailable action into existence. Code owns schemas, state identity, budgets, and enforcement.
5. Write a concise current assignment and an observable stop requirement. Keep the original request separately with its reasoning owner. A stop requirement is not a statement that the evidence already exists. Do not overload a small decision prompt with the entire authoring procedure or simultaneous planning and execution goals.
6. Define the branches and returns: missing text goes to the designated text helper; difficult queries, ambiguity, repeated unhelpful actions, or unsupported progress return to the reasoning owner; safety or missing authority returns to the authorized human/owner; worker DONE returns evidence for independent review. Specify exactly what each handoff carries and where approved continuation resumes.
7. Define replacement semantics. A human or authorized reasoning owner may revise the current assignment. Invalidate its pending choice and generated arguments; preserve the original request unless the human changes it. Scope policy history to the assignment without deleting the complete audit trail, resetting global limits, losing browser/process identity, or replaying mutations.
8. Walk the contract on a success, absent-evidence case, failure/escalation branch, and human override. Use the triggering case and a materially different application/capability level. Ensure stronger models have no expanded authority and weaker models need not infer missing transitions. Distinguish walkthroughs from actual trials.
9. Within existing test authority, compare against the baseline using the smallest meaningful observable check. Count preparation/observation, scoring/serving, argument generation, execution, retries, verification, and escalation in total-task cost and latency. Preserve incorrect early DONE and useful BLOCKED outcomes in the evidence. Keep the simpler path when end-to-end benefit is absent. Existing explicit evaluation waivers and human-controlled scope remain in force.

## Output and completion
Return one coherent workflow contract: actor responsibilities, required inputs, offered operations and their execution mapping, concise assignment/stop, conditional handoff packets and return points, permission boundaries, and a bounded evidence check. State what is implemented, what was tested, and what is still hypothetical. The authoring task ending, a model returning, and the user's task succeeding are different events. Stop affected work for an unresolved owner, missing permission, unavailable operation, conflicting completion test, or unverified consequential action.

## Portability and evidence
Paste this procedure into the workflow-authoring agent's context and load the application-specific contracts it calls for. Do not paste it verbatim into every decision-model call. The source discussion used browser examples to motivate explicit assignment boundaries and missing action coverage; those examples and measurements are not bundled qualification evidence and do not prove this procedure works universally. A navigation model selecting a page control and a stronger routing model selecting a supported worker are different applications of the same contract, not evidence of identical model quality. Experimental measurements belong with their actual authorized evidence owners, not duplicated or assumed to be available here.
