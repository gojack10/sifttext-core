## Core Command

**Repair supported defects before presentation or persistence; do not invent violations to satisfy the review.**

After the mandatory Commit pull, read applicable instructions in the assigned local project and Knowledge Layout. Reuse unchanged instructions already loaded. Do not require an absent private instruction tree.

For ownership, reuse the deepest existing owner of the question; separate a governing question from its answer and independently testable work. Alternatives belong beneath their common question, not beneath a competing answer. Grow unknown subproblems only when evidence exposes them. Scope states the question and acceptance boundary; the stable micro-summary helps select it; the body holds answer, rationale, evidence and next bounded step. A fresh reader must find the relevant owner from the outline, then recover inputs, dependencies, success check and stop condition from that owner. Preserve explicit human priorities and deferred branches.

Status follows the node's own acceptance claim, not activity or child aggregation. Active direct children block or reopen resolved parents; intentional deferrals carry a resume condition. Decisions, implementations and real-use checks prove different things. Keep useful evidence outside discarded ancestry and preserve meaningful rejected attempts as separate nodes. Knowledge Layout and Worktree Publication own the native field/state contracts.

Before alleging a violation, identify the governing clause, the observed mismatch and any applicable example or exception. Distinguish an existing violation, an underspecified instruction and a newly requested convention. An optional arrangement is not forbidden merely because another arrangement is preferred. If the evidence does not establish a violation, say so.

Repair supported defects within the authorized write scope. When a required or task-relevant read reveals a supported rule violation, include the smallest repair in the current SiftText Commit proposal, even if that node was not in the initial delta. Name the rule, the observed defect, the affected node and the exact proposed change. Do not scan unrelated trees for cleanup. A proposal does not expand write authority. Apply only approved or standing-authorized repairs; keep out-of-scope repairs pending, and stop only work that depends on them. If the human postpones a repair, retain its defect and resume condition rather than report it fixed. If ownership, authority or the intended correction remains ambiguous, inspect the affected context or ask only for the missing decision. Do not broaden the project or introduce unaccepted answers.

## Forced Repairs

### 1. Preserve distinct rejected attempts

Any distinct failed attempt becomes a discarded probe node, either `[+][x]` for a new discarded node or `[!][x]` when updating an existing discarded node.

The native format has no `ruled_out` metadata. Keep a small local qualification in the body; preserve distinct rejected approaches as discarded nodes with reasons and evidence.

Failure pattern to repair:

```text
Wrong: Ruled out: tried A, B, C, and D.
Right:
[+][x] Probe A — discard reason...
[+][x] Probe B — discard reason...
[+][x] Probe C — discard reason...
[+][x] Probe D — discard reason...
```

### 2. Remove DRY violations

State lives in children and source nodes, not repeated prose. Remove duplicated volatile state from the delta. Use links to hubs/source-of-truth nodes instead of restating state in multiple places. Apply the ownership test above before collapsing structure: a question hub and its sole answer child are not duplicate state merely because there is one child. Remove duplicated detailed answers and checkpoints, not the distinct question/answer responsibilities.

### 3. Remove one-hop structural links and TOC prose

Direct parentage and ordered children are already available through native child symlinks/order files and SQLite Queries. Links are for >1-hop references, cross-tree references, or orthogonal branches that structural navigation does not expose.

Hard rule: do not add links to direct parents or direct children. If prose needs the parent or children, refer structurally: "read parent", "read children", "the parent owns this invariant", or "the child named X contains the probe." The structure carries identity; a link duplicates it.

Parent content must not enumerate its children. Child content must not link back to its parent. Remove child lists, parent links, comprehensive child link directories, and manual tables of contents from prose.

An ordered mandatory/conditional reading or execution sequence for an instruction pipeline is operational behavior, not a redundant directory of children. Preserve the necessary sequence while avoiding a copied child inventory. Use structural child names for one-hop references; do not create redundant parent/child links.

### 4. Fix probe placement

Apply the parentage test above. Distinguish a contribution or answer to a governing question from an extension that depends on an established result. Alternatives belong beneath their common question, not beneath the winner merely because it won. Chronology alone establishes neither relationship.

### 5. Verify field placement

Place information in the appropriate field rather than putting everything in `content`.

- **see_also** — explicit graph references with target UUID and reason; include required dependencies where appropriate
- **discarded nodes** — independently meaningful rejected approaches, with `discard_reason`
- **warnings** — guardrails, things to never do or always check
- **content** — the node-owned answer or current checkpoint, its rationale, evidence, limitations, and continuation; not a running transcript of unrelated work
- **scope** — what question the node explores
- **micro_summary** — stable-purpose navigation context, not current progress or the next assignment

Use dedicated Vitals fields for their navigation and guardrail roles. A brief warning may also appear in content when needed to understand the answer; its detailed evidence remains with its owner. Remove duplicated detailed state, not useful synthesis or necessary qualifications.

### 6. Fix diff clarity

Operation marker goes left; status marker goes right. Existing unchanged context has no operation marker and shows only its status.

Examples:

```text
[~] Existing in-progress context node, unchanged
[ ] Existing not-examined context node, unchanged
[x] Existing discarded context node, unchanged
[!][~] Existing in-progress node to update
[+][ ] New not-examined node
[+][x] New discarded node
[→][~] Move existing in-progress node
[←][x] Add link to existing discarded node
[-][x] Delete existing discarded node
```

Do not render the whole subtree as if it is new. Show only affected parents/children plus enough unchanged context for orientation.

### 7. Make executable instruction pipelines explicit

When the delta creates or changes executable instruction nodes, read and apply [[Canopy (Prompt Authoring Framework)|957aa569-75be-4871-b376-6b1943cc4db4]] before presenting or persisting it. Verify the affected entrypoint, role assignment, required read order, default steps, conditional branches, outputs, return path, human override path and completion/stop conditions. Repair unstated transitions and contradictory linked instructions within the approved scope; do not accept a collection of related rules as an executable procedure. Ordinary knowledge-node edits do not trigger this extra review. If correction would exceed the approved scope, report the affected gap rather than silently expand it.

Walk the proposed instructions as the intended executor: identify the first available assignment, its actual input requirements, completion check, result recipient, and continuation after success, missing evidence, or contradiction. If any transition requires guessing, repair the proposal before presentation. Apply Canopy’s authoring and exact-change presentation requirements rather than duplicating them here. Check that actual proposed link operations are visible under Dialogue’s existing rendering rule; do not expand the link graph to satisfy that presentation check.

When a changed field is also consumed as executable instruction content, verify that the delivery path will still supply the required instructions after the change. If that cannot be established, stop the affected field changes and identify the consumer and missing check; do not silently replace executable instructions with descriptive navigation text. This is a delivery-compatibility check, not permission to implement a new mechanism.

## Output Discipline

The Forcing Pass is normally silent: apply it to the draft, then present the repaired tree delta. If the human asks what changed, explain the repairs. If the pass leaves a suspicious `ruled_out`, DRY duplication, or child link in parent prose, explicitly defend it in one sentence.

## Frontier Completeness Gate
Before displaying or persisting a delta, demonstrate frontier completeness for each affected current accepted design or outcome. Account for every independently testable commitment as satisfied with evidence; unfinished with an owning node and acceptance test; or explicitly deferred, rejected or superseded with its reason.

Compare design against actual capability, not only the existing node inventory, so missing commitments are discovered. Runtime diagrams do not substitute for work ownership. Then simulate continuation from the proposed outline: identify the intended owner, next bounded action, required dependencies, success evidence and stop condition, or the exact pending human decision.

If this requires source-chat reconstruction, an unexpanded diagram or guessed work, repair the delta before presentation. Pending branch priority does not excuse an undefined frontier within each branch. Apply the gate to the affected current outcome closure, not every historical design in the forest. Preserve bounded dependency reads and do not manufacture a node per runtime stage.

### MVC check

Apply the two-stage outline-then-owner navigation check above to the affected area. Record which owners the outline exposes and which node reads supply the required decision or action. Compare those owners with the known obligations in the changed content. Repair a missing owner, a misleading summary or a stale body at its source; a statement that the tree is complete is not evidence. Check what the reader needs and what it can safely skip.

Run the complete native candidate check before and after persistence/reconciliation; it counts Markdown content bodies with `o200k_base` and rejects more than 5000 tokens per body. This is not a count of all metadata fields. Ordinary Git commit alone is not this gate. Report generated link/context overhead separately; do not repair it by deleting necessary authored content or navigation. Apply the existing semantic checks as well: a passing count alone does not prove proper decomposition or sufficient context.
